# Security implementation checkpoint

The implemented boundary is a synthetic-data-only local demonstration. `packages/policy` is the sole decision point for the one allowlisted action. A separate `apps/demo-broker` child process owns its private SQLite deduplication store, a fixed local scheduler child process, and the only handle capable of stopping that scheduler. The authority reaches it through bounded Node private IPC. The app, an agent, and callers never supply a PID, executable path, arbitrary command, Docker socket, or arbitrary health URL.

## Enforced behavior

- Authenticated principal records, current organization membership, incident commander identity, revocation, and roles come from the policy database. Caller-provided roles and `user_confirmed`-style flags have no authority.
- The immutable action digest covers organization, incident, authenticated requester, action, target identity and generation, strict empty parameters, live/simulation mode, graph/policy/recovery versions, creation time, and a random nonce. Approval adds a short expiry to its binding digest.
- Only the current incident commander can approve. The requester cannot self-approve. Participants and agents cannot execute; only an authenticated service principal with `execution_service` authority can cross the dispatch boundary.
- A SQLite `BEGIN IMMEDIATE` transaction atomically consumes an approval and assigns one stable execution ID. The action has one execution row, concurrent actions for the same target generation are serialized, and the broker deduplicates the same execution ID durably before attempting the effect. Broker lookup authenticates and checks the action/generation binding before returning an existing receipt.
- Current principals, commander, incident state, versions, expiry, target generation, and digest are rechecked immediately before dispatch. Generation mismatch fails closed.
- Simulation traverses authorization and reservation but never calls the broker. A crash after reservation is reconciled under the existing execution ID; absence of a broker receipt becomes `outcome_unknown` and never triggers a guessed redispatch.
- Verification combines a fixed-loopback scheduler probe, a healthy fixed-loopback control probe, and broker-owned process state. A broker receipt is not verification. Missing observer/control evidence produces `outcome_unknown`.

## Actual containment claim

The real effect is stopping a disposable Node scheduler child spawned inside the separate broker process from a fixed local source path, using `spawn` with `shell: false`. The scheduler and control observer listen only on `127.0.0.1`; ephemeral ports are reported through broker startup IPC rather than accepted from an action. Only the broker-owned child handle with the startup-pinned random generation can be stopped. This demonstrates narrow process stopping and restart-safe authorization/deduplication; it does not demonstrate container, network, kernel, host, malware-eradication, or production isolation. The authority and broker still share the same macOS user and host, so same-user malware remains outside the proven boundary.

The policy and broker use separate SQLite databases. Their local commits are not cross-database atomic. `packages/response` supplies the trusted bridge: it loads a stored canonical proposal by scope and ID, validates its current graph, cited evidence, incident, fallback, expiry, and fixed verification plan, and binds the proposal digest plus a separate response-context digest to one policy action. The context digest covers the incident, fallback, graph records, response tasks, and all current incident evidence; it detects operational-context changes that the graph structure revision alone does not represent. The same checks and target generation run again after reservation immediately before broker dispatch. Retrying the same binding returns the existing action; a changed binding is rejected rather than creating another executable action.

Verified-outcome projection reads the authoritative bound action, approval, execution, broker receipt, and observer facts. It also rechecks the current policy target is enabled and still has the exact organization, identity, and generation. It rejects simulation, unknown/failed state, wrong scope, changed proposal digest, replaced or disabled target, mismatched receipt execution ID, stale receipt or observation, or any result other than scheduler unreachable, healthy control, and stopped broker-owned process. It writes structured generation and observer facts with a deterministic evidence ID derived from the execution ID. It also writes a second deterministic graph-state fact through the fixed internal mapping from `pantry-demo-scheduler` to canonical node `scheduler`; callers cannot select that mapping. The target-bound fact retains authenticated, independently verified containment provenance for fallback approval while its subject security trust remains `unknown`; the graph fact likewise marks scheduler availability `unsatisfied` and security trust `unknown`. Stopping the subject does not declare it clean or trusted. A crash before or between the two domain writes can be retried after restart: each fact is projected once, and an existing identical record returns idempotently, including after an identical concurrent-write conflict. This is idempotent reconciliation across two stores, not a cross-database atomic commit. There can still be a temporary interval where verified policy state exists without one or both domain facts; callers must run projection reconciliation after restart. Projection deliberately fails closed if the target generation rotates or the observations become stale before reconciliation. Verified stopping proves the narrow scheduler state at the observation time; it does not establish that the original service was clean or that an incident was eradicated.

The MCP surface has no approval, execution, evidence-write, actor-management, shell, filesystem, or infrastructure tool. Proposal submission binds the authenticated actor inside the workflow service rather than trusting `authorActorId`. Authority configuration is strictly validated against canonical actor and organization records, credentials bind the actor revision, and every scoped tool call rechecks the current actor, revision, and membership. Tests show an already-connected client loses access after an actor revision change. Tool callbacks return a fixed rejection shape rather than leaking raw database, filesystem, or validation messages. The local configuration file and bearer token remain same-user demo secrets rather than a production identity system.

## Verification

Run `node --test packages/policy/test/policy.test.ts packages/response/test/coordinator.test.ts`. Twenty-one tests cover the allowed real stop, organization and target scope isolation, untrusted caller flags, role separation, changed target/parameters/mode, stale versions, post-approval database mutation, approval expiry, concurrent replay, same-target serialization, zero-effect simulation, revoked authority/target generation change, crash after reservation, a persisted nonterminal broker marker, durable denial audit, observer failure and recovery, stored-proposal idempotency, projection restart and partial projection restart, context change before dispatch, target-generation replacement before projection, actual simulation rejection, and an actual live effect with unavailable observer. The crash-marker test proves reconciliation returns `outcome_unknown` while the scheduler remains running and does not redispatch based on a timeout guess. Projection tests inject failures before the first domain write and between the two domain writes, close both domain and policy databases, reopen them with new store and policy instances, and prove one event per deterministic fact while retaining the original broker attempt. They also prove canonical scheduler state becomes unavailable with unknown trust and verified fallback dependencies make distribution available. This is durable database-reopen fault-injection evidence, not a SIGKILL or full process-crash proof. Broker IPC requests and startup/close operations have deadlines; startup failure terminates only the owned broker child. The full `npm test` run passes 60 tests, the authority/MCP integration suite passes, and `npx tsc --noEmit` verifies the shared TypeScript build.

The independent communications review found that the mesh separates signed hop custody from signed recipient acknowledgment and confines payloads to coordination message kinds. A relay cache was initially populated before its persistence transaction committed, which could overstate relay ciphertext evidence after queue rollback. The communications implementation now uses durable `seen` state, and its regression test proves a queue-rejected message leaves no seen record or decryptability evidence. Recipient receipts also bind the original sender and SHA-256 of the complete canonical protected envelope inside the recipient signature. An adversarial regression uses B's real signing key and a different B-authored ciphertext with A's message ID; C accepts and signs that substituted envelope, but A rejects the valid C receipt because its durable outbound sender and envelope digest differ, then accepts the receipt for the genuine A envelope. Physical three-device or radio mesh remains unverified.
